> ⚠ 2026-09-09:本文是历史排障记录,部署流程以最新笔记为准;当前 ACT/filter 部署边界只有 active 模式,冒烟确认后必须通过显式人工确认执行真机控制。

> 项目：`/home/fanshihao/Desktop/dev/ICRA2027_TELEOP`  
> 任务：Task2 `power_button_press_v1` / `button_press`  
> 目标：打通 `prepare -> train -> evaluation -> checkpoint promotion -> 真机遥操部署 -> rosbag 审计` 全链路。

## 1. 最终结论

2026-09-06 完成了 Task2 Filter 的全链路工程验证：

1. 从 `act_train_ready` 批量准备训练数据，并提取双相机 SigLIP2 视觉特征；
2. 使用合格 episode 完成 Filter round1 训练；
3. 在 3 个 held-out episode 上完成离线评估；
4. 将 checkpoint 晋升为带 SHA-256 固定的运行时配置；
5. 将 learned filter worker、ROS adapter 和 model deployment supervisor 接入 GUI 真机采集流程；
6. 在部署边界接入后确认 Filter 以 5 Hz 连续产生候选，并将候选、观测和诊断话题纳入 rosbag。

这里的“链路打通”是工程结论，不等于模型效果已经达标。round1 的 correction 概率接近 0，当前仅完成候选输出与审计链路验证，尚未进行主动接管真机控制的验收。

## 2. 最终链路

```text
act_train_ready 中的成功 episode
        |
        v
质量门 + rosbag 导出 + correction view
        |
        v
双相机帧提取 + SigLIP2 embedding（1536 维）
        |
        v
filter_training_vlm.jsonl
        |
        v
ConditionalTrajectoryVAE 训练（27 train + 3 validation）
        |
        v
trajectory_filter.pt + training_report.json
        |
        v
held-out evaluation
        |
        v
promoted runtime YAML（checkpoint + SHA-256）
        |
        v
learned_filter_worker <Unix socket> learned_filter_ros_adapter
        |
        v
model_deployment_supervisor
        |
        v
teleop_control_bridge -> 真机机械臂
```

该验证阶段 Filter 会计算并发布候选，但 supervisor 在候选缺失或不安全时把原始 LinkerTA 指令作为控制输出。因此可以采集和评估模型行为，同时不让 round1 模型直接修改真机动作。

#### 问题 4：ROS 环境污染 Conda Python，导致 Torch/Transformers 导入失败

**现象**

VLM prepare 阶段出现依赖导入失败。进一步检查发现 Conda 的 Python 继承了 ROS 注入的 `PYTHONPATH`，错误加载 Ubuntu 系统目录中的旧版 SymPy/Numpy，而不是 `teleop` 环境内版本。

**根因**

同一个终端先 source ROS，再激活 Conda 后，`PYTHONPATH` 中的 `/usr/lib/python3/dist-packages` 等路径污染了训练进程。

**解决办法**

在训练/VLM/运行时入口中显式执行：

```bash
export PYTHONPATH=""
```

保证 GPU worker、Torch 和 Transformers 使用 `teleop` 环境自己的依赖栈。

**代码改动**

- 修改 `scripts/prepare_vlm_filter_view.sh`；
- 修改 `scripts/task2_prepare_filter_data.sh`；
- 修改 `scripts/task2_train_filter.sh`；
- 修改 `scripts/start_learned_filter.sh`；
- 修改 `tools/encode_images_with_vlm.py`，在依赖导入失败时打印真实异常类型与消息。

#### 问题 5：Prepare 中断后残留输出目录，重跑会拒绝覆盖

**现象**

VLM 编码中断时会留下不完整的输出目录。再次 prepare 时，脚本看到目录已存在便报 `refusing to overwrite`，无法自动续跑。

**根因**

程序只以目录是否存在判断任务是否完成，没有区分“完整结果”和“中断残留”。

**解决办法**

在 `scripts/prepare_vlm_filter_view.sh` 中用最终文件
`filter_training_vlm.jsonl` 作为完成标志：

- 目录存在但最终文件不存在：视为不完整派生数据，删除后重算；
- 最终文件存在：继续保持拒绝覆盖，防止破坏有效结果。

这样批量 prepare 可以在瞬时失败后继续执行，不需要重做已经完成的 episode。

#### 问题 12：ROS adapter 启动即失败，线程池字段与 rclpy 冲突

**现象**

adapter 启动时异常，Filter 无法真正加入遥操链路。

**根因**

`tools/learned_filter_ros_adapter.py` 使用 `self.executor` 保存 `ThreadPoolExecutor`，与 rclpy Node 自己的 `executor` 属性冲突。

**解决办法**

将字段改名为 `self.thread_pool`，并同步修改 submit 和 shutdown 调用。

#### 问题 13：旧 Unix socket 造成 adapter `ConnectionRefusedError`

**现象**

worker 正在加载大模型时，启动脚本看到旧的 `/tmp/teleop_learned_filter.sock` 已存在，误判 worker READY，立即启动 adapter，随后连接被拒绝。

**根因**

启动就绪判断只检查 socket 文件是否存在；上一次异常退出留下的 socket 文件形成竞态。原 10 秒等待时间对 checkpoint + SigLIP2 加载也偏短。

**解决办法及代码改动**

- `scripts/start_learned_filter.sh` 在启动 worker 前删除旧 socket；
- `tools/learned_filter_worker.py` 在慢速模型加载前再次清理 socket，形成双保险；
- 等待循环由约 10 秒延长到最多约 120 秒；
- adapter 强制退出时捕获重复 `rclpy.shutdown()`，避免无意义的关闭 traceback。

**验证结果**

独立运行 worker + adapter 75 秒：worker READY、adapter 成功连接，未再出现 `ConnectionRefusedError`。

#### 问题 18：第二路 RealSense 有 publisher，但没有实际图像帧

**现象**

- `/camera2/camera/color/image_raw` 有 publisher；
- `ros2 topic hz` 在 8 秒内没有数据；
- `camera2.log` 持续报告：

```text
Frames didn't arrived within 5 seconds
```

**根因**

round1 是严格的双相机 1536 维模型，运行时相机顺序为 `[main_rgb, auxiliary_rgb]`。camera2 无帧时，adapter 的完整性检查会提前返回，不向 worker 提交推理。这是输入不完整触发的正确保护行为。

**解决办法**

- 检查并重新连接 camera2 的 USB 线、供电或 USB 端口；
- 先用下面命令确认 camera2 恢复稳定出帧：

```bash
ros2 topic hz /camera2/camera/color/image_raw
```

- 恢复后重启/继续 GUI 会话，让 adapter 完成历史窗口 warmup。

**最终验证**

camera2 恢复后日志连续出现：

```text
[diag] infer submit request
[diag] infer response ready=True reason=None
```

候选话题实测：

```text
/teleop_filter/right_arm_joint_control
```
